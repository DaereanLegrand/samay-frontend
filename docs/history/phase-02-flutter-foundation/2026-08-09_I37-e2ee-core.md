## 2. Key decisions

1. **`info` is raw bytes in `hkdfSha256`** — RFC 5869 TC2's info is non-ASCII; the ASCII domain strings go through `utf8Bytes()`. Verifiable against RFC 5869 TC1/TC2 (both locked as known-answer tests).
2. **Skipped keys carry per-entry insertion timestamps** (`skippedKeyInsertedAt`, serialized as `"at"` in the session JSON) — the §4.6 30-day pruning needs per-entry ages; the spec JSON sketch doesn't include them, so I added the field (deviation, S-07 input).
3. **Session JSON also stores `dhs_pub`** alongside `dhs_priv` — §8.3 lists only the private key; the public is derivable but storing it keeps `fromJson` synchronous and auditable. (Public key is on the wire anyway in every envelope header.)
4. **The type-0x02 envelope header is 114 bytes, NOT the 112 printed in §6.4** — see MISTAKE-1. The field table is authoritative.
5. **`E2eeSessionStore` deals in raw JSON strings** (§8.3 format), not `RatchetState` objects — the store stays dumb (lifecycle fields only: `last_used_at`, `peer_ik_dh` for the index); the state machine lives in `E2eeSession`. This deviates from §10.4's `Future<RatchetState?> loadSession` sketch.
6. **`E2eeMessageCipher.encrypt` returns the base64url String** (mission contract), matching §6.6 storage; §10.4's "Uint8List" sketch is satisfied by `base64UrlNoPadDecode` on the wire.
7. **In-memory sessions also enforce the 90-day expiry** (`_handleRatchetEnvelope`), not only on store load — otherwise a long-idle app could still decrypt after expiry.
8. **X3DH ephemeral is never persisted**; the session keeps only EKA public + spk_id/opk_id for the one-time init envelope (§5.3 step 4).
9. **OPK private keys are deleted on BOTH init success and auth-failure paths** (R1 §3.4/§5.4) — the server consumed the OPK at bundle fetch regardless; keeping it only preserves decrypt capability for replays.
10. **`cryptography_flutter` and the flutter_secure_storage bump to ^11 are NOT in this change** — mission says minimal diff (`cryptography` only). `cryptography` 2.9.0 falls back to pure Dart automatically. The platform-accelerated variant (`FlutterCryptography.instance` in main.dart) + fss 11 bump are I-38/S-18 follow-ups.

## 3. MISTAKEs (searchable)

### MISTAKE-1: E2EE-ARCHITECTURE.md §6.4 "112 bytes" is an arithmetic typo — the wire header is 114 bytes
The spec's field table for type 0x02 (magic 4 + version 1 + type 1 + ik_dh 32 + ik_sig 32 + dh_pub 32 + pn 4 + n 4 + ct_len 4) sums to **114**, but the document prints "= 112". I coded 112. Result: parse read `ct_len` at offset 108 instead of 110 and sliced the ciphertext 2 bytes early — every ratchet envelope failed AEAD with a mysterious `[0x00 0x1a]` prefix (the first two bytes of the real ct_len, value 26). Diagnosed by instrumenting `ratchetEncrypt` (correct 26-byte output) vs the parsed envelope (28 bytes). Fixed `ratchetHeaderSize` to 114 with an explanatory comment. **S-07/V-06: the spec doc should be corrected; 112 is impossible from the field sizes.**

### MISTAKE-2: NIST AES-256-GCM vector memorized incorrectly
My remembered `ct=42831ec2…`/`tag=5bc94fbc…` is the AES-128 case-3 pair, not the AES-256 case-4 pair. The `cryptography` package output was correct (verified byte-for-byte against Python's `cryptography` library: `522dc1f0…`/`eb9f796c…`). Test now locks the Python-verified values.

### MISTAKE-3: Test-side record confusion — `final (h1, c1)` vs named record `({header, ciphertext})`
Initially typed `ratchetEncrypt`'s return as a named record; destructuring with positional patterns caused 20+ analyzer errors. Switched to positional `(RatchetHeader, Uint8List)`.

### MISTAKE-4: `library;` directives placed after imports
Six files failed `library_directive_not_first`; moved to the top (after the doc comment).

### MISTAKE-5: session restart test created fresh stores
`_Party` built new `MemoryE2eeKeyStore`/`MemoryE2eeSessionStore` per instance — a "restart" produced an EMPTY session store, so the restarted object re-ran X3DH (type-0x01 init) instead of resuming. Fixed with `restartSession()` over the same stores. Same class of bug: the fake prekey server generated republish OPKs into the FETCHER's key store instead of the OWNER's — B could never find the fresh OPK private key.

### MISTAKE-6: test data for the 90-day sweep
"Swept" sessions in the store tests were dated 100 days before the sweep clock — they were legitimately expired. Fixed fixture dates.

## 5. Known-answer notes for S-07

- HKDF: RFC 5869 TC1 (L=42) and TC2 (L=82) — validates the `cryptography` Hkdf `nonce`-as-salt mapping.
- X25519: RFC 7748 §6.1 — validates seed-as-scalar semantics of `newKeyPairFromSeed`.
- AES-256-GCM: NIST case-4 (96-bit IV, empty AAD), cross-checked with Python.
- X3DH SK equality: tested via two independent implementation paths (initiate vs respond) on fixed key material; a true "by-hand" SK KAT is not feasible manually (the whole point of the DH+HKDF chain), so the suite instead pins the primitives with RFC KATs + full-flow equality. If S-07 wants a recorded SK vector, generate one from `_bobFixture`-style fixed seeds and freeze it — the fixtures are deterministic.
- Ratchet: determinism tests (same SK → identical chains) + 200-message convergence + PN bookkeeping asserted in the multi-turn test.

## 7. Open questions for I-38 / S-07

1. **§6.4 "112" vs 114** — spec typo; I-38 must build against 114 (see MISTAKE-1). D-07 should fix the doc.
2. **Simultaneous-init cross (D-11)**: last-processed-wins replaces the local session; when BOTH sides' init envelopes cross, each side keeps a different X3DH run and the first post-cross messages are dropped (documented, tested). Sesame's multi-session fallback (try all sessions on decrypt) is post-MVP — I-38 UX should expect occasional drops.
3. **SPK signature persistence**: `spk.meta` now carries `sig` (extra field vs §8.2 sketch) so `currentSignedPrekey()` can republish without re-signing. `opk.meta` carries `next_id` (extra field) for id allocation.
4. **`has_sent_init` is session-state, not ratchet-state**: initiator restarts after the first send resume with 0x02; a restart BEFORE the first send re-runs X3DH with a fresh bundle (session was never persisted — correct, the peer never saw the old one).
5. **`E2eeKeyStore.loadOneTimePrekeyPrivate` + `deleteOneTimePrekey` are consumed by the cipher** (I-38 does not need to manage OPKs); `publishAll`/`fetchBundle` RPCs are I-38's Supabase work (§9.3).
6. **`cryptography_flutter` acceleration** (hardware AES/X25519 on iOS/Android via `FlutterCryptography.instance` in main.dart) and the `flutter_secure_storage ^11` bump were deferred per mission scope — S-18/S-02 to evaluate.
7. **90-day expiry enforcement added in-memory too** (see decision 7) — I-38's foreground sweep can call `sweepExpiredSessions()` on the store.
