## Context

AUTH spec gap (`docs/specs/steps/phase-03-auth-profiles/AUTH-signup-login.md` §"Ban Enforcement"): the
Go CLI (`USRS` ban) writes `users.banned_at`/`ban_reason` (migration `20260510000001_full_schema.sql:48-49`)
but the app never checks it — banned users keep logging in and keeping their (still-valid) JWT.
The planned fix was an Edge Function auth hook, but `supabase/functions/` does not exist yet.

**Research (sources cited in the final report):** a GoTrue JWT stays valid until expiry after a ban; the
server-side blocking hook is the real boundary. Two standard approaches:
(a) client-side: check `banned_at` on every app start / auth state change, force sign-out + ban screen,
(b) server-side: block token refresh (needs a Supabase Auth Hook — out of scope).
This agent implements (a); the server-side handoff is documented below.

## What was built

1. **`BanService`** (`lib/core/services/ban_service.dart`, new)
   - `checkBanStatus({bool force})` → `BanStatus { isBanned, reason }` — reads `users.banned_at, ban_reason`
     for the current user via the user's own RLS path (`users_read_own`, full_schema.sql:610).
   - Graceful edge cases: no session → not banned (pre-signup); no `users` row → not banned (pre-signup);
     `banned_at` null → not banned. DB/network error → **fail-open** (logged): a false positive would sign
     out every user on a transient error — strictly worse than a temporarily-visible session. The
     authoritative enforcement is server-side.
   - **Short cache** (30 s, per user id) so the auth-state listener does not hammer the DB on every token
     refresh; `force: true` bypasses the cache at security-relevant boundaries; in-flight coalescing
     dedupes the concurrent signedIn-event + method checks.
2. **Auth gate** (`lib/core/providers/auth_provider.dart`)
   - `AuthState` gains `banned` (bool, default false) + `banReason` (String?) — backwards compatible.
   - New `_authStateForUser(user, {forceBanCheck})` helper runs the ban check after **every** auth
     success path: session restore (`_resolveInitialState`), `initialSession`/`signedIn`/`tokenRefreshed`
     events, `signIn`, `verifyOtp`. Banned → `signOut()` + state `AuthState(banned: true, banReason)`.
   - The `signedOut` event handler preserves a previously-set `banned` state (the ban sign-out itself
     emits `signedOut`; without this the guard would bounce the user to login).
   - Ban-check failure fail-open at the notifier level too (never blocks authentication).
3. **Router guard** (`lib/core/router/auth_guard.dart`) — `data.banned` short-circuits the guard **before**
   the public/authenticated checks: ANY route (public or not) redirects to `RoutePaths.banned`; the ban
   route itself renders (no loop).
4. **Ban screen** (`lib/features/auth/banned_screen.dart`, new) — minimalist black per
   `docs/design/DISCO-DESIGN-SYSTEM.md` §1 (P1 black always, P2 white core): white `Icons.block`
   (`AppIconSizes.xxl`), 'Cuenta suspendida' title (`displayMedium` — auth-flow header per §3.2), the
   stored ban reason (`Motivo: {reason}`, falls back to a default body), one outlined `VButton`
   "Cerrar sesión" (`profileSignOut` ARB key) → `signOut()`. No other actions.
5. **Route** — `RoutePaths.banned = '/banned'` (top-level, static, no params); registered in
   `app_router.dart` beside `/welcome` (I-03's hardened builder style kept).
6. **ARB keys** (es template + en, metadata + placeholders, parity guarded by `test/l10n/l10n_test.dart`):
   `bannedTitle`, `bannedDefaultBody`, `bannedReasonLabel({reason})`. Ran `flutter gen-l10n`.
7. **Coordination unblock for I-36** (see MISTAKE/Issues): while holding the ARB locks, added I-36's 12
   pending ARB keys (`profileCosmetics`, `profileNoCosmeticsYet`, `profileAvatarUpdatedSnack`,
   `profileAvatarChange`, `interest*` × 8) so the shared tree compiles again. I-36 owns the final wording.

## Issues found / reported (not fixed — out of scope)

- **Server-side enforcement handoff (S-03/S-10 or EEDG track):** research shows Supabase Auth Hooks now
  provide a free/Pro **Custom Access Token hook** that runs before every token issuance — including
  `authentication_method: token_refresh` (Supabase docs, cited in report). A `custom_access_token_hook`
  Postgres function that returns `{"error":{"http_code":403,"message":...}}` when
  `SELECT banned_at FROM public.users WHERE id = ...` is set blocks sign-in AND refresh — the clean
  replacement for the never-built `auth-ban-check` Edge Function. Migration + `supabase_auth_admin`
  grants pattern documented in the auth-hooks docs.
- **Edge Functions still don't exist** (`supabase/functions/`) — EEDG/FLMT track.
- **`users_update_own` still allows clients to clear their own `banned_at`** (mass-assignment, G-03;
  full_schema.sql:611-612) — a client could un-ban itself in the DB; the RLS/column-restriction fix
  belongs to I-32/S-03. The client check is a UX gate, not a boundary.
- **Session `tokenRefreshed` re-check is cache-aware (30 s)** — a ban lands at worst within ~30 s of the
  next auth event on an open session; app restart / any sign-in is immediate (`force: true`).
- **TODO.md blocked:** `docs/to-fix/TODO.md` was held by I-37 for the whole task; the H-32 status flip
  (client-side enforcement DONE, server-side hook open) is left for I-37's release or the orchestrator.
