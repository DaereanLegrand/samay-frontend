# D4-chat-ui — 2026-08-15 — Group chat UI (ISSUE 4, presentation tier)

Status: COMPLETE (RED → GREEN → VALIDATE → DOCUMENT)

## What was built

- **D4a — `ChatThreadView`** (`lib/features/chat/widgets/chat_thread_view.dart`):
  the 1:1 thread extracted from `ChatScreen` into a reusable
  `ConsumerStatefulWidget` — `ChatThreadView({required chatId, String? groupId})`.
  Owns exactly what the old screen body owned: the three realtime channels
  (messages/reads/deletes + dispose), `_markRead`/`_markMessagesRead`
  (first-load via `ref.listen` + live arrival), `_checkPeerReinstall` (skipped
  when `groupId != null`), the messages `AsyncValue` (loading/error/data),
  date chips, the pagination header, long-press delete bubbles, the composer
  (VInput + flat-white VButton) and `_sending`. The internal helpers
  `_DateEntry/_DateChip/_MessageBubble/_MessageStatus/_olderHeader` moved
  with the thread; bubble keys `chatBubbleOwn-<id>`/`chatBubblePeer-<id>` are
  byte-identical.
- **D4b — thin `ChatScreen`**: AppBar title from the inbox row's
  `peerUsername` (the group name for group chats — server RPC) or
  `l10n.chatTitle`; body = VAurora (α0.04 peach) + `ChatThreadView`, with
  `groupId` resolved from the inbox row (`referenceId` when `type == 'group'`).
- **D4c — `ChatInboxItem.referenceId`**: `row['reference_id']` mapped into the
  model (constructor + `fromRow` + `copyWith`).
- **D4d — group rows in the inbox**: `type == 'group'` rows render
  `Icons.group` in the 44px avatar square instead of the initial letter; name/
  preview/unread unchanged.
- **D4e — `groupChatIdProvider`** (groups_providers.dart): a
  `FamilyAsyncNotifier<String?, String>` with `ThrottledRefresh` over
  `groupsRepositoryProvider.getGroupChatId(groupId)` (RPC-backed lookup of the
  `chats` row `type='group'` + `reference_id`).
- **D4f — group detail Chat tab**: `_buildChatTab()` now watches
  `groupChatIdProvider(widget.groupId)` — loading → `VLoadingView`, error →
  `ErrorView` with retry (invalidate), data null → the existing honest
  placeholder (`groupsChatOneToOneTitle/Body`), data → `ChatThreadView(chatId,
  groupId: widget.groupId)`. Only the method body changed; the invited branch,
  hero, and Info/Miembros/Eventos tabs are untouched (B owns them).

## Decisions made and why

- The sender label lives INSIDE the peer bubble (WhatsApp convention), above
  the message text, styled `labelSmall` + `mutedStrong` (AA informational
  text, §2.4). Own bubbles never label.
- Sender resolution: `groupMembersProvider(groupId).valueOrNull` (member rows
  carry `users.username` via the `user_search_view` join); loading/error of
  the members provider degrade to the uid-prefix fallback — never crashes.
- `_checkPeerReinstall` is 1:1-only (no single peer session in a group
  thread), and 1:1 bubbles render byte-identical to the pre-extraction tree.
- `_buildChatTab` returns `ChatThreadView` unwrapped (a full-height Column —
  not inside `_scrollableTabBody`, same as `GroupEventsTab`).

## MISTAKE

- `_peerBubble` used `Theme.of(context)` without a `context` parameter after
  the extraction — analyze caught it (`undefined_identifier`); fixed by
  passing the `BuildContext` down. Lesson: when moving widget helpers, verify
  implicit-context usage; `dart analyze` is the safety net.

## Unverifiable / notes

  is missing `_buildChatTab` shows the honest placeholder (kept the existing
  copy). The live sender-name path depends on `get_chat_inbox` returning
  `reference_id` (server RPC — assumed per the D3 handoff; the mapper is
  defensive: absent key → null → 1:1 behavior).
- Live realtime + end-to-end send/decrypt in a real group thread was not
  exercised (needs the stack up); the widget is covered hermetically with the
  same seams the 1:1 screen tests already use.
