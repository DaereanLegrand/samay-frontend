## What was built

### 1. `lib/shared/widgets/skeletons.dart` — the skeleton API (NEW)

Four const-constructible skeletons, all `VShimmer` compositions of U-06's `VShimmerBox`/`VShimmer` primitives — `surfaceAlt #111111` blocks, sharp corners (§4.2), no color (§5.8), reduced-motion-gated by `VShimmer` (§7.5):

| Widget | Shape | Row/card anatomy |
|---|---|---|
| `VSkeletonList({rows = 6, padding})` | avatar **circle** + 2 lines per row, 1px `hairline` separators | my_groups / notifications / leaderboard rows |
| `VSkeletonGrid({rows = 2, columns = 2, padding})` | N §5.3-style cards (`surface` fill + hairline border) with cover + 2 lines | future grid/hub layouts |
| `VSkeletonProfile({avatarSize = avatarLarge})` | hero avatar circle + name/handle/2 body lines | profile-hero loading |
| `VSkeletonDetail({rows = 4, padding})` | feed `_EventCard` geometry: 140px cover + title/date/location lines, hairline borders | feed |

- **Avatar circle = the one deliberate §5.8 shape exception** (documented in the library doc): the real `ProfileAvatar` is circular, so a square block would read as a layout bug. §4.2's "sharp corners" governs blocks; the doc lists no circle ban.
- **Scroll-safe by construction**: every skeleton wraps its rows in a `SingleChildScrollView(physics: NeverScrollableScrollPhysics())` — full layout (deterministic row counts for tests), overflow clipped, zero RenderFlex errors at 320×568 (§7.3, U-19's zero-overflow rule applies to loading states too — RED-proven: the first GREEN run overflowed the 600px test viewport by 352px).
- **`disableAnimations` handling is VShimmer's** (U-06/U-18): static gray blocks, no `ShaderMask`, zero tickers — asserted per skeleton.

### 2. First-load wiring — the 4 heaviest list screens

| Screen | Before (U-21) | After (U-22) | Reload behavior |
|---|---|---|---|
| `feed/screens/feed_screen.dart` | `VLoadingView` | `VSkeletonDetail()` | list stays visible (`skipLoadingOnRefresh: true`) |
| `groups/screens/my_groups_screen.dart` | `VLoadingView` | `VSkeletonList()` | list stays visible (`skipLoadingOnRefresh: true`) |
| `groups/screens/leaderboard_screen.dart` | `VLoadingView` via `VStateView(loading: …)` | `VSkeletonList(rows: 8)` hoisted beside `VStateView` | list stays visible (`rankings == null && isLoading` guard) |
| `notifications/.../notification_center_screen.dart` | `VLoadingView` | `VSkeletonList()` | list stays visible (`skipLoadingOnRefresh: true`) |

**Decision (documented per the mission's "your call per screen"):** skeletons only when there is **nothing on screen**; pull-to-refresh keeps the list visible. This is a deliberate improvement over the old behavior where a refresh replaced the whole list with the spinner (`AsyncValue.when`'s `skipLoadingOnRefresh: true` on feed/my_groups/notifications; the `valueOrNull == null && isLoading` guard on leaderboard, whose `VStateView` keeps its error/empty duty — **`state_views.dart` was NOT modified**). Error/empty/reload paths are byte-identical otherwise.

## Decisions made and why

- **Skeletons only on first load, list stays during refresh:** `skipLoadingOnRefresh: true` (feed/my_groups/notifications) + `valueOrNull == null && isLoading` (leaderboard). The skeleton stands in exactly when the user would otherwise stare at a blank spinner; pull-to-refresh no longer blanks the list (previously the spinner replaced it). `state_views.dart` untouched (`VStateView` keeps error/empty duty on the leaderboard).
- **Avatar circle exception:** the real avatar is a circle; a square skeleton block would mislead the eye. Everything else is sharp-cornered per §4.2.
- **Scroll-safe skeletons:** fixed-height rows × N exceed small viewports; the non-scrollable `SingleChildScrollView` keeps all rows laid out (deterministic tests) while clipping overflow — no RenderFlex errors on 320×568 (§7.3).
- **`rows` defaults sized to the screens:** list 6 (≈ one viewport), leaderboard 8, detail 4 (≈ one viewport of 140px cards), grid 2×2.
- **Left untouched (documented candidates, NOT in this mission):** group_detail (3× `VLoadingView` — hero + tabs), shard_ledger, cosmetics, photo_gallery, party_finder, minigames, profile screens, friends screens, events screens, chat — they keep `VLoadingView`; the API (`VSkeletonProfile`, `VSkeletonDetail`) is ready for a follow-up pass (U-23..U-25 handoffs).
- **No integration-suite changes:** the feed/notifications/groups flows pump real screens but settle past the (instant) loading frame; no flow asserts loading states — adding skeleton assertions there would be timing-flaky. Verified unchanged.
