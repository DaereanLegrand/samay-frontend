## Decisions made and why

- **Mission-brief paraphrase vs doc — `inputDecorationTheme` label:**
  the brief said "label muted" (`#666666`); DISCO-DESIGN-SYSTEM §5.2 (THE
  CONTRACT) pins the label at `mutedStrong #999999` — the doc's own "fix
  from #666666 — current label fails 1.4.3 at normal size" (§2.4). Same
  resolution as U-01's hairline-vs-border call: **the doc wins.** The
  theme-level label is `mutedStrong`; the legacy `muted`/`#444444` labels
  on `v_input.dart` remain U-05's restyle scope (explicit styles win, so
  the theme is inert for VInput anyway).
- **`progressIndicatorTheme` = white, not pink:** §5.8 is explicit —
  full-screen loading is white; `glowPink` is "accent variant for brand
  moments (welcome, checkout)" only. The theme default must be the
  non-brand moment. It also matches the pre-theme rendering exactly
  (raw spinners used `colorScheme.primary` = white).
- **`tabBarTheme` minimal (indicator + label white, nothing else):** the
  mission asserts "indicator white" only. Setting `unselectedLabelColor:
  muted` would drop tab labels to 3.66:1 — below the 4.5:1 AA bar §2.4
  requires for informational text (and M3's default onSurfaceVariant keeps
  AA). Setting `labelStyle` would churn the 4 existing TabBars. Both
  deliberately left to defaults; U-30/U-26 can revisit.
- **Value-equality of `SamayTheme.dark` is a contract:** the I-65 theme
  persistence tests pin `expect(app.theme, SamayTheme.dark)`. My first
  checkbox `fillColor` used `WidgetStateProperty.resolveWith` (closure —
  identity-hashed) which silently broke ThemeData `==`. Fixed with
  `WidgetStateProperty.fromMap({WidgetState.selected: white})` — value-
  equal (`WidgetStateMapper` uses `mapEquals`), and `resolve({})` returns
  null (border-only, exactly the M3 unselected look).
- **`TextButton.styleFrom(overlayColor:)` in Flutter 3.44.1 takes the BASE
  color** and derives the per-state alphas itself (pressed α0.1 / hover
  α0.08 / focused α0.1 via a fromMap). Passing α0.1 directly would have
  double-dimmed the press feedback. Passed `AppColors.white` (§5.1 "α0.1
  white overlay on press").
- **Disabled checkboxes keep the white fill** when selected: the palette
  has no grey tinted fill (deliberate simplification, documented in the
  theme comment). M3 would render onSurface@0.38 — not a §2 token.
- **No integration_test addition:** the mission's verification gate is
  `flutter test` (test/ only). Theme composition is asserted at the
  unit level (`test/theme/`); widget-rendering regressions are covered by
  the full suite's 1707 tests. U-29 owns the integration UI smoke.

## MISTAKE

- **Bad edit (self-inflicted, fixed):** my first insertion edit into
  `app_theme_test.dart` accidentally deleted the body of the
  `registers the SamayThemeExtension` test (left a dangling opener).
  Caught by reading the file before running; restored the body verbatim.
  Lesson: verify the surrounding context after every structural edit,
  not just the edited region.
- **SDK-version API assumptions (×3, fixed):** (1) `TabBarTheme` vs
  `TabBarThemeData` — 3.44.1's `ThemeData.tabBarTheme` is
  `TabBarThemeData`; (2) `TooltipThemeData` has no `backgroundColor`/
  `shape` — it takes a `decoration`; (3) `SnackBarThemeData` has no
  `surfaceTintColor`, and `TextButton.styleFrom`'s `overlayColor` is a
  base color. All caught by the analyzer/compiler before any behavior
  landed — the daily log's "grep the SDK first" discipline saved time.
- **Value-equality regression (found by the test suite, fixed):** the
  `resolveWith` checkbox fill broke `SamayTheme.dark == SamayTheme.dark`
  (see Decisions). The I-65 persistence tests caught it immediately —
  this is exactly why ThemeData equality is worth pinning. The theme
  comment now warns against `resolveWith`.
