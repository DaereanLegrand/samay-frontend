## What was built

### 1. `android/app/build.gradle.kts` — release signing contract (fail-fast)

- **`keystoreEnv` map** reads the four §3.3 env vars (`ANDROID_KEYSTORE_PATH`,
  `ANDROID_KEYSTORE_ALIAS`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS_PASSWORD`) from `System.getenv` — the ONLY signing source.
  No `key.properties` file, no keystore in the repo (android/app/keystores/
  stays absent; `**/*.jks` gitignored).
- **`signingConfigs.create("release")`** only when all four envs are set;
  `buildTypes.release` signs with it. When any env is unset, `signingConfig =
  null` — the release buildType never falls back to the debug key (the old
  `signingConfigs.getByName("debug")` line is GONE).
- **Fail-fast guard (always registered, task-time):** a `doFirst` on
  `assembleRelease` / `bundleRelease` / `packageRelease*` throws a clear
  `GradleException` when (a) any keystore env is unset — "Android release
  signing is not configured: set the §3.3 keystore envs … Release builds
  NEVER fall back to the debug key" — or (b) the keystore file is missing at
  `ANDROID_KEYSTORE_PATH`. Mirrors the M-18 Fastfile
  `assert_credentials_configured!` guard semantics: release-shaped builds
  cannot run with placeholder/missing signing, ever.
- **`kotlinOptions` → `compilerOptions` migration (build-blocking):** Gradle
  9 turns Kotlin-DSL deprecation warnings into compile ERRORS — the first
  `flutter build apk --debug` failed on `kotlinOptions` (kotl.in/u1r8ln).
  Migrated to `kotlin { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }`
  (KGP 2.2.20 DSL). This also unblocks M-21's CI `build.yml` debug build.
- Debug builds keep the default debug signing (untouched).

## Decisions made and why

- **Gradle 9.4.1 kept, `-all` variant:** the project was scaffolded by the
  Arch AUR flutter (`.metadata` revision `archlinuxaur…`), which pinned AGP
  8.11.1 + KGP 2.2.20 + Gradle 9.4.1. Flutter 3.44.1's template default is
  9.1.0 and its validation tables "know" up to 9.3.1 — but those tables are
  conservative (they'd also flag 9.1.0 for KGP 2.2.20, whose documented max is
  8.14). The empirical test is the ground truth: **`flutter build apk --debug`
  succeeds on this machine with 9.4.1 + AGP 8.11.1 + KGP 2.2.20 + JDK 21**, and
  M-21/M-22's CI docs already pin this exact wrapper+JDK17 combo. Changing the
  version would (a) require a network download of a distribution not in the
  cache and (b) churn CI docs — for no demonstrated benefit. Documented in the
  wrapper properties comment; a future regeneration of android/ by a newer
  Flutter should re-run this analysis.
- **`-all` over `-bin`:** Flutter's own template ships `-all`; the local cache
  has the `-all` distribution fully downloaded (`.ok` marker) — switching let
  the validation build run offline, and makes CI deterministic against the
  same artifact. One-time ~200MB CI download cost vs `-bin`; accepted for
  template parity + reproducibility.
- **Task-time guard, not configuration-time:** a config-time `check()` would
  break `flutter build apk --debug` (envs are unset in dev/CI-debug), since
  build.gradle.kts is evaluated for every invocation. The `doFirst` guard
  fails only when a release-packaging task actually runs — exactly the
  fail-fast semantics the mission demands, leaving debug builds untouched.
- **`signingConfig = null` (never debug) when envs unset:** even if the guard
  were ever bypassed, release would produce an UNSIGNED artifact (which fails
  device install), never a debug-signed one — defense in depth behind the
  clear-message guard.
- **Wrapper committed despite the Flutter template gitignoring it:** flutter_tools
  auto-injects a missing wrapper at build time (that's why the template ignores
  it), but M-21 flagged that as an unverified CI dependency. A committed
  wrapper makes the build deterministic with zero runtime regeneration. The
  cost: the committed gradlew/jar must be updated when Flutter's bootstrap
  changes (rare; the jar is distribution-agnostic).
- **`kotlinOptions` → `compilerOptions`:** not gold-plating — the first real
  build FAILED on it (Gradle 9 deprecation-as-error). Required for ANY gradle
  9.4.1 build including M-21's CI debug build. Byte-identical behavior
  (jvmTarget 17).

## MISTAKE / gotcha

- **MISTAKE (hit + fixed):** first manifest edit placed an XML comment INSIDE
  the `<application>` start tag — invalid XML. Caught by `xmllint --noout`
  (XML OK) after moving the comment above the tag. Lesson: verify XML after
  edits, not only grep.
- **MISTAKE (hit + fixed):** the opt-008 distributionUrl grep used
  regex-escaping (`https\\://` in double quotes) which BSD grep (macOS)
  does not resolve — the pinned-string probe falsely failed. Fixed with
  `grep -Fq` (fixed-string) — the exact string now matches.
- **Gotcha (hit + fixed):** the wrapper `gradle-wrapper.jar` from the flutter
  cache artifact is dated 2017 — this is NORMAL (the bootstrap jar is
  distribution-agnostic and reads `distributionUrl` from the properties);
  verified it is the same artifact flutter_tools injects (`injectGradleWrapperIfNeeded`),
  so committing it is exactly what the tool would copy.
- **Gotcha (checked, not hit):** gradle 9.4.1 + KGP 2.2.20 → the flutter
  doctor tables flag "newer than known" — that validator is doctor-only, not a
  build gate; the real build passed (see Verification).

  `flutter build apk` = RELEASE mode → it now FAILS FAST without the keystore
