## Decisions made and why

- **The workflow references secret NAMES only, never values — and the names
  ARE the §3.3 env names.** The M-17/M-18 lanes read a fixed env-var set
  (`REQUIRED_CREDENTIAL_ENV` / `REQUIRED_ANDROID_CREDENTIAL_ENV`), so the
  GitHub secret names are the same strings 1:1 — the fastest, least-inventive
  mapping. The doc lacked exact names (R25 said `CI_*`/`SIGNING_*`/`STORE_*`),
  so per the mission I ADDED the exact 16 names to R25 (locked).
  `ANDROID_KEYSTORE_BASE64` is the one invented name: the `.jks` is binary, so
  the keystore *content* cannot share the path contract name
  (`ANDROID_KEYSTORE_PATH` is a PATH env, materialized at runtime).
- **Pre-guard shape: `if: ${{ secrets.X == '' || … }}` → step runs and exits
  1.** When everything is set the step is SKIPPED (GitHub's `if:` semantics)
  and the job proceeds. This is the mission's "guard step fails fast if the
  secrets are unset/placeholder" — I chose `== ''` (unset) as the check: the
  M-17/M-18 lane guards are the placeholder-VALUE layer, the pre-guard is the
  unset layer. A never-created secret evaluates to `''` in the expression, so
  the guard is safe for not-yet-provisioned repos. Secrets are available in
  step-level `if:` for push-triggered workflows (the fork-PR secret restriction
  does not apply to tag pushes).
- **Credential FILES are materialized at runtime — and the paths MUST differ
  from the §3.3 placeholder strings.** The lane guard treats
  `ENV[name] == placeholder` as "not configured", so a CI env pointing at the
  literal §3.3 path (e.g. `fastlane/keys/google-play-service-account.json`)
  would abort the lane even with the file present. Materialized paths:
  `fastlane/keys/AppStoreConnect_<KEY_ID>.p8` (conventional name, key-id
  derived), `fastlane/keys/play-service-account.json`, and
  `android/app/keystores/release.jks`. All under gitignored (`fastlane/keys/`)
  or transient (keystores) dirs — nothing can be committed; `make
  secrets-check` stays green.
- **The Fastfile's `dart_defines` helper skips unset vars** (define-free dev
  parity, I-34) — but the workflow still PRE-GUARDS on `SUPABASE_URL` +
  `SUPABASE_ANON_KEY`: a "release" built without them would compile and then
  fail fast at runtime by I-34 design. The guard makes that failure loud and
  early instead of shipping a broken binary.
- **`make bundle-install` instead of bare `bundle install`:** the M-15/M-17
  contract makes the Makefile the only Ruby entrypoint (Gemfile presence gate,
  pinned by opt-008) — identical effect, repo-consistent.
- **gh CLI instead of a third-party release action** (softprops
  etc.): gh is preinstalled on ubuntu-latest, `GITHUB_TOKEN` is automatic, and
  `gh release create` + `gh release upload --clobber` covers create-or-update.
  Zero new supply-chain surface; the mission's "upload-release-asset" intent
  is met by the standard CLI.
- **`cancel-in-progress: false` for release only:** cancelling a release run
  mid-upload could leave a half-attached asset; PR/push workflows keep the
  cancel-superseded behavior (M-20/M-21).
- **Artifact paths come from the Fastfile's own contracts** (M-17
  `build/ios/ipa/*.ipa`, M-18 `build/app/outputs/flutter-apk/app-release.apk` +
  `bundle/release/app-release.aab`) — the workflow validates + uploads exactly
  what the lanes promise to produce.

## MISTAKE / gotcha

- **MISTAKE (hit + fixed in the workflow):** my first draft pointed the lane
  path envs at the §3.3 placeholder paths (`fastlane/keys/google-play-service-account.json`,
  `android/app/keystores/release-keystore.jks`) — which would make the M-17/M-18
  guard abort on STRING EQUALITY even with the files materialized. Re-read the
  Fastfile guard (`ENV[name].to_s == placeholder`), switched to distinct
  materialized paths, and documented WHY in the workflow + README. Caught
  before writing the workflow file (guard re-read).
- **Gotcha (checked, not hit):** GitHub steps don't share shell exports —
  the materialized path envs go through `$GITHUB_ENV` (same pattern as
  build.yml's stack env).
- **Gotcha (checked, not hit):** secrets preserve newlines — the `.p8`/JSON
  secrets can be pasted raw (multi-line PEM/JSON). Only the keystore needs
  base64 (binary). Documented in the README checklist.
- **M-21's handoff said "7 secrets"; the real contract is 16.** The M-17/M-18
  guards require the FULL §3.3 env set (iOS 8 incl. FASTLANE_USER, Android 6,
  plus 2 dart-define names). The README lists all 16 (names only) and calls
  out the 7 core iOS store secrets; this log documents the divergence
  explicitly.
- **Pre-existing (reported, NOT fixed — out of scope, M-27's file):** the
  android gradle release buildType still signs with the DEBUG key
  (`android/app/build.gradle.kts:37`) — M-27 wires `signingConfigs` to the
  keystore envs. Until then a CI `release_play` run could technically produce a
  debug-signed AAB; the lane guard + pre-guard make sure it can't even START
  before the real keystore secrets exist, but a REAL store upload stays
  M-27-blocked. Also still open (M-21's report, unchanged): the gradle wrapper
  is incomplete in the tracked tree (gradlew/gradle-wrapper.jar absent).
- **Pre-existing (reported, NOT fixed — M-19's file):** `Gemfile.lock` is
  still absent by design — `make bundle-install` in CI will generate it on the
  first release run; M-19 commits it after the first real `bundle install`.
