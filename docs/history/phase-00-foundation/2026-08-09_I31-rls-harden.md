## Decisions made and why

- **`SET search_path = ''` + full qualification over `SET search_path = public, extensions`**: the safest minimal path (Juega pattern, `20260724000001` precedent). `pg_catalog` builtins (now(), floor, GREATEST, jsonb_build_object, interval, NULLIF) need no qualification — pg_catalog is implicitly searched even with an empty search_path. The two trigger functions with zero body object references still get the SET clause (consistency + future-proofing).
- **`public.rank_bracket` / `::public.size_tier` / `::public.rank_bracket`**: with empty search_path, the enum type used in `DECLARE` and casts must be explicitly schema-qualified or it won't resolve.
- **All 12 functions re-created `public.`-qualified**: prevents a poisoned-search_path CREATE from ever landing the function in a non-public schema.
- **No `ALTER ROLE service_role BYPASSRLS`**: the role already HAS BYPASSRLS (Finding). Adding it would be a no-op at best and a wrong precedent (and it would only matter for a role that doesn't exist → migration error) at worst. Instead the finding is locked in via the migration COMMENT + pgTAP 38c, so a future image change that drops BYPASSRLS fails the schema test loudly.
- **signup_tracker re-forced in the same migration**: idempotent, keeps the hardening statement complete (31/31), satisfies "all 31 RLS-enabled tables".
- **plan-count rule** (DEVELOPMENT-WORKFLOW §3.5): tests = `^\s*SELECT ` lines − plan − finish − nested SELECTs inside `ok(NOT EXISTS(...))`. New file: 176 − 1 − 1 − 1 = **173**.
- **No stack started** (mission constraint): verification is 100% static; live `supabase db test` happens at the checkpoint after I-02's remap.

## Finding — service_role BYPASSRLS (critical for FORCE RLS safety)

- Repo evidence: `supabase/volumes/db/init/` is **empty** (no custom role SQL; SELFHOSTING.md §5: "no auto-init SQL"), and neither `supabase-testing/docker-compose.yml` nor `supabase/docker-compose.yml` creates DB roles. Roles come from the `supabase/postgres:17.4.5.2` image's baked-in `/docker-entrypoint-initdb.d/`.
- Upstream verification (static, no docker): `github.com/supabase/postgres` — `Dockerfile-17:158` does `COPY migrations/db /docker-entrypoint-initdb.d/`, and `migrations/db/init-scripts/00000000000000-initial-schema.sql:31` reads `create role service_role nologin noinherit bypassrls;` — confirmed at commit `8d32169739d` (2025-04-23, the 17.4.x image era) and still present in `develop`.
- **Conclusion: service_role HAS BYPASSRLS.** Postgres semantics: FORCE RLS forces the *table owner* to obey RLS; superusers (`postgres`) and roles with BYPASSRLS (`service_role`) still bypass. The Go admin CLI (`internal/db/client.go:22` — `SUPABASE_SERVICE_ROLE_KEY` via PostgREST as `service_role`) is therefore **NOT broken** by FORCE RLS. No ALTER ROLE needed.
- **MISTAKE (avoided):** assuming "if service_role lacks BYPASSRLS" — the repo contains no init scripts to check, so the only correct verification was the upstream image source. I did not `docker run` anything (Juega's stack is live; Samay's compose still maps 5432/54321 — I-02's remap).
- **Pre-existing count discrepancy (report):** SUP-03/SEC-14/G-02 said "11 of 12" / "~14 of 16" SECURITY DEFINER functions. Actual current inventory (post-`handle_signup` drop): **13** SECURITY DEFINER functions; `check_signup_email` already hardened → **12 hardened by I-31**. The 12 listed in my mission match exactly.
