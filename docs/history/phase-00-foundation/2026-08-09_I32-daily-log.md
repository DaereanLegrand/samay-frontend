## Decisions made and why

- **SECURITY INVOKER trigger (deliberate deviation from mission sketch's "SECURITY DEFINER")**: inside a SECURITY DEFINER function `current_user` becomes the function owner (postgres, superuser) → the BYPASSRLS/superuser gate would be true for every caller → the trigger would never block anyone. SECURITY INVOKER keeps `current_user` = the PostgREST effective role (`SET ROLE authenticated|service_role`). `session_user` is unusable too (PostgREST always connects as `authenticator`). No privilege escalation: invoker function runs with caller privileges. Documented in migration comment as MISTAKE-avoided.
- **Column REVOKE (not RLS) for column restrictions**: RLS policies cannot restrict columns; the standard PostgREST-safe approach is column-level `REVOKE UPDATE`. The trigger adds defense-in-depth and is the ONLY way to express the one-way `deleted_at` rule (set = soft-delete, clear = blocked) — the client's `softDeleteUser()` legitimately sets `deleted_at`, so a full block would break account deletion.
- **Trigger INSERT normalization**: `users_insert_own` allowed minting arbitrary balances at signup; the trigger forces the app_config grant value (the app reads the same key → no flow break) and NULLs ban/delete/subscription fields.
- **REVOKE lists validated against every client write site in `lib/`** (auth_service softDeleteUser/createUserProfile, edit_profile bio, group_service createGroup/updateGroup/inviteMembers, event_service createEvent/updateEvent, media_service uploadEventPhoto, notification_service, moderation_service): no revoked column is legitimately client-written. `rank_bracket` INSERT left open (createGroup writes the 'b0_20' default; nightly recalculate_ranks overwrites) — residual documented.
- **is_group_member() SECURITY DEFINER + STABLE**: canonical Supabase pattern for group-scoped access checks; SECURITY DEFINER (owner postgres) bypasses RLS → zero recursion risk (the 20260512000006 bug class); STABLE is mandatory for functions used in policies (VOLATILE rejected). `SET search_path = ''` per I-31 convention.
- **group_members_insert empty-group heuristic removed**: under RLS-filtered subqueries, `NOT EXISTS (SELECT 1 FROM group_members ...)` is true for any non-member (they see no rows) → anyone could join any group; replaced with creator-self + promotor-invite branches (both pinned to auth.uid()).
- **Admin RPC GRANT service_role**: Go CLI (`internal/db/client.go`) calls them as service_role; pg_cron runs as postgres (superuser — unaffected by REVOKE).
- **plan-count rule** (I-31/D-04): 207 `^\s*SELECT ` lines − plan(1) − finish(1) − nested-in-ok(1) = **204**.

## MISTAKE blocks (for future devs)

- **MISTAKE (avoided)**: SECURITY DEFINER trigger would silently no-op (current_user = postgres). If a future dev "hardens" `assert_safe_user_update` to SECURITY DEFINER, the G-03 block evaporates — the pgTAP 39b `prosecdef` assertion exists to catch this.
- **MISTAKE (avoided)**: gating on `session_user` breaks the service_role path (PostgREST session_user is always `authenticator`).
- **MISTAKE (avoided)**: "empty-group" INSERT heuristic was bypassable under RLS — every self-referential policy expression must assume the subquery only sees the caller's own rows.
