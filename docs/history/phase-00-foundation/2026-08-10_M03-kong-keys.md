## Research: does Kong 3.9 expand `${VAR}` inside kong.yml at runtime?

**No.** Verified three ways:

1. **Kong source** (`kong/db/declarative/init.lua` at tag `3.9.0`): zero
   matches for `getenv` / `os.getenv` / `environ` / `substitut` — the
   declarative config loader has no env handling.
2. **Kong docs** (db-less mode page, 3.9.x): the declarative file is loaded
   as-is; no env substitution documented.
3. **The official Supabase pattern exists precisely because of (1):** the
   official `docker/volumes/api/kong-entrypoint.sh` (kong/kong:3.9.3 — the
   exact pinned image) performs the substitution itself, via **awk**:

```sh
# Substitute environment variables in the Kong declarative config.
# Uses awk instead of eval/echo to preserve YAML quoting (eval strips double
# quotes, breaking "Header: value" patterns that YAML parses as mappings).
awk '{
  result = ""
  rest = $0
  while (match(rest, /\$[A-Za-z_][A-Za-z_0-9]*/)) {
    varname = substr(rest, RSTART + 1, RLENGTH - 1)
    if (varname in ENVIRON) {
      result = result substr(rest, 1, RSTART - 1) ENVIRON[varname]
    } else {
      result = result substr(rest, 1, RSTART + RLENGTH - 1)
    }
    rest = substr(rest, RSTART + RLENGTH)
  }
  print result rest
}' /home/kong/temp.yml > "$KONG_DECLARATIVE_CONFIG"
```

The official `kong.yml` therefore holds `$SUPABASE_ANON_KEY` /
`$SUPABASE_SERVICE_KEY` (single-`$` refs) and the official compose passes
`SUPABASE_ANON_KEY: ${ANON_KEY}` / `SUPABASE_SERVICE_KEY: ${SERVICE_ROLE_KEY}`
into the kong container env.

**Syntax consequence:** the awk regex is `\$[A-Za-z_][A-Za-z_0-9]*` — it
handles `$VAR`, NOT `${VAR}` (the braces would survive substitution and leak
into the key). The mission's `${ANON_KEY}` spelling was therefore replaced by
the verified `$ANON_KEY` — same names, official syntax.

## Decisions made and why

- **Mirror the official supabase pattern (entrypoint awk), not Kong-native
  interpolation** — Kong 3.9 does not interpolate declarative config; the
  official pattern is proven on the exact pinned image (kong/kong:3.9.3).
- **`$ANON_KEY` / `$SERVICE_ROLE_KEY` refs (bare `$`)** — the mission's
  `${ANON_KEY}` syntax does not survive the official awk (braces leak);
  documented as a deliberate, verified deviation. Container env names follow
  the mission (ANON_KEY/SERVICE_ROLE_KEY), fed from the existing `.env`
  `SUPABASE_*` keys (no `.env` duplication; compose defaults are the
  `.env.example` placeholder values as mandated).
- **Resolved config path `/usr/local/kong/kong.yml`** — the official output
  path; source template stays at `/api/kong.yml` (now `:ro`, so the awk can
  never write into the committed host file).
- **Storage/studio envs left untouched** — the mission scope is the kong
  gate; storage's `ANON_KEY`/`SERVICE_KEY` and studio's
  `SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_KEY` still hardcode `your-*`
  placeholders (pre-existing; affects only storage's internal PostgREST
  client and Studio's dashboard client, not the opt-test paths). Reported as
  a handoff (S-06/S-08) instead of scope creep.
