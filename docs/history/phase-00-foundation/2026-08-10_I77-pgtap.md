## Decisions made and why

- **`col_is_unique` over `has_unique`**: pgtap.org docs — `has_unique(table)` only
  tests "the table has a unique constraint" (any), while `col_is_unique(table,
  columns)` tests the exact column set (diagnostics list the found sets). The
  column-pair form is the one that catches "UNIQUE dropped / narrowed".
- **`pg_constraint` ok() over `has_check`**: `has_check(table)` is any-check-only
  (verified docs) and `col_has_check(columns)` matches the check's *columns*, not
  its name; the 23514 contract in opt-002 names the constraint
  (`check_casual_no_preshards`), so the assertion is name+table+type anchored.
- **`trigger_is` over nothing**: all 9 triggers were already asserted via
  `has_trigger`; the binding check is cheap, static, and guards the §5 triggers'
  function wiring (the 20260512000007 cast fix re-CREATEd update_group_size_tier
  — a binding drift there would now fail loudly).
- **Body LIKE asserts kept coarse** (`%…%` on unquoted fragments) so whitespace/
  qualification changes don't false-fail; every pattern was grep-verified against
  the CURRENT hardened bodies in 20260809000001.
- **No live-DB behavior tests** (mission constraint): full-cap pruning behavior
  (1000+1 inserts → 1000 retained) needs a running DB — pgTAP body asserts +
  opt-003's below-cap retention are the static coverage; the live run happens at
  the checkpoint (I-31/I-32/I-76 deferred the same way).
- **Header migration count updated** instead of leaving "23": I-63's 0006 was
  covered by §45 but the header lagged; D-04's §3.5 rule is "mirrors stay
  structurally identical" — both files keep the identical header (the
  I-31-precedent is byte-identical files).

## MISTAKE / gotcha

- **MISTAKE (avoided):** first draft of 46b used a `%''large''::public.size_tier%`
  pattern (quoting the enum literal with embedded quotes inside a SQL string
  literal — brittle). Replaced with the unquoted `member_count >= 257` /
  `member_count >= 15` threshold fragments.
- **Gotcha (pgTAP API):** `has_check` and `has_unique` do NOT take a constraint
  name / column list (docs verified) — using them for the named-check and
  column-pair asserts would have silently passed on a broken schema. Only
  `col_is_unique` and the pg_constraint query carry the exact contract.
- **Gotcha (plan math):** each new `ok(EXISTS (SELECT 1 FROM pg_constraint…))`
  adds BOTH an assertion AND a nested SELECT line; forgetting the +2 nested would
  miscount (310 − 1 − 1 − 4 = 304, not 306).
