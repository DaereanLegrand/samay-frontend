## Root cause (M-01's diagnosis, confirmed)

`volumes/api/kong-entrypoint.sh` was mounted **over** the image's
`/docker-entrypoint.sh`:

```yaml
volumes:
  - ./volumes/api/kong-entrypoint.sh:/docker-entrypoint.sh
entrypoint: []
command: /docker-entrypoint.sh
```

and its body ran `until kong health` (which can never pass — the wrapper
never starts kong) then `exec /docker-entrypoint.sh kong docker-start` —
which, with the mount in place, re-executes **itself** → infinite recursion →
kong never healthy → `docker compose up -d --wait` blocked.

## Critical verification: the real entrypoint of the pinned image

The mission assumed the image entrypoint is `/usr/local/kong/docker-entrypoint.sh`
(the GitHub `kong/docker-kong` master / `3.9.3`-tag layout). **That is wrong
for the published image.** Verified via the Docker Hub registry API (config
blob, metadata only — no layer download, no pull):

- `kong/kong:3.9.3` (amd64, OCI index) image config history:
  `COPY build/dockerfiles/entrypoint.sh /entrypoint.sh`,
  `ENTRYPOINT ["/entrypoint.sh"]`, `CMD ["kong" "docker-start"]` — the
  **legacy** layout, base Ubuntu 24.04 (bash present at `/bin/bash`).
- Same for the locally-present `kong/kong:3.9.1` (Juega's): confirmed its
  live container (healthy, RestartCount=0) runs the wrapper → nginx, i.e.
  `exec /entrypoint.sh kong docker-start` is the proven-working invocation.
- The Kong deb packages (debian bookworm + ubuntu noble, 3.9.1) contain NO
  entrypoint — `/entrypoint.sh` comes from the Dockerfile layer only.

Therefore the wrapper's final line is `exec /entrypoint.sh kong docker-start`.

## What was built

### 1. `supabase/volumes/api/kong-entrypoint.sh` + `supabase-testing/volumes/api/kong-entrypoint.sh` (rewritten, byte-identical, MD5 `c8fd3753…`)

- `#!/usr/bin/env bash` + `set -Eeuo pipefail` (mirrors the official Kong
  `docker-entrypoint.sh` style). Interpreter note: `set -o pipefail` is not
  supported by POSIX `/bin/sh` (dash) — the mission's "POSIX sh + pipefail"
  pair is mutually exclusive; bash is guaranteed in the image (Ubuntu base).
  The compose `entrypoint` therefore invokes `/bin/bash` explicitly.
- **Bounded DB wait** (`DB_HOST` default `db` — the compose service key, valid
  in both stacks; `DB_PORT` 5432; `DB_WAIT_ATTEMPTS` 60 × `DB_WAIT_INTERVAL`
  2s, all env-overridable): TCP connect via bash `/dev/tcp` (no pg_isready /
  curl / nc in the kong image), clear `[kong-entrypoint]` logging, **hard
  fail (exit 1) on timeout** so `restart: unless-stopped` retries loudly
  instead of silently starting a gateway whose upstreams are down.
- **No templating** — `kong.yml` is static (mounted at `KONG_DECLARATIVE_CONFIG`).
- **`exec /entrypoint.sh kong docker-start`** — the image's REAL entrypoint
  with the exact args its CMD carries.
- Idempotent (no temp files/state), LF-only.

## Decisions made and why

- **Verified the published image instead of the repo layout.** The GitHub
  `3.9.3` tag ≠ the Docker Hub image (legacy `/entrypoint.sh` layout). Trust
  the registry config blob + Juega's proven 3.9.1 container over the repo
  file. This is why the mission's `/usr/local/kong/docker-entrypoint.sh`
  assumption was NOT used.
- **Keep kong.yml static with placeholder keys.** Mission-mandated: "keep the
  key-auth placeholder plugin config … do NOT embed real keys". The mismatch
  (kong.yml placeholders vs `.env` keys vs opt-test embedded keys) is real
  and documented as the MKE/S-10 handoff (row 22 stays open).
- **Hard-fail on DB-wait timeout** (exit 1 + restart) rather than starting a
  gateway whose upstreams are unreachable — surfaces the failure at
  `docker compose up -d --wait` instead of a silent broken stack.
- **`/bin/bash` entrypoint (deviation from official `/bin/sh`)** — required
  by `set -o pipefail` and `/dev/tcp`; bash verified present (Ubuntu 24.04
  base of the published image). Documented in the wrapper header.

## MISTAKE / gotcha

- **Gotcha (research):** the mission's assumed entrypoint path
  (`/usr/local/kong/docker-entrypoint.sh`) exists only in the GitHub repo
  layout; the published 3.9.x images use `/entrypoint.sh`. Cross-checking the
  registry config blob (no pull) avoided shipping a wrapper that would
  `exec` a nonexistent file and keep kong crash-looping.
- **Gotcha (research):** Kong's deb packages ship no entrypoint at all — the
  `COPY build/dockerfiles/entrypoint.sh /entrypoint.sh` layer is what creates
  it. The old-layout source is not in `Kong/docker-kong` history (images
  built from a legacy pipeline); the registry config blob is authoritative.
- **Gotcha:** `set -o pipefail` is illegal under dash (`/bin/sh`) — "POSIX
  sh" and "pipefail" cannot both hold; documented instead of silently
  dropping pipefail.
- **MISTAKE (avoided):** my first opt-007 edit accidentally deleted the
  final "All compose static checks passed" echo line; caught by re-reading
  the tail, restored, then ran the gate green.
- **Pre-existing (untouched, per mission):** compose `healthcheck: kong
  health` (M-01's) is a valid 3.9.x subcommand — left as-is; the image's own
  `kong-health` HEALTHCHECK is overridden by compose anyway.
