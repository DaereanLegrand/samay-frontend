## Decisions made and why

- **Three independent jobs, not one big workflow step list:** independent
  jobs report red/green separately on the PR (analyzer vs Go vs static
  gates), run in parallel, and a failure in one never masks the others.
  "Fail-fast" = GitHub's default per-step semantics inside each job (first
  failing step fails the job; no `continue-on-error`), documented in the
  README.
- **`flutter-version: 3.44.1` exact pin, NOT `flutter-version-file`:** the
  mission says "use the installed SDK (3.44.1) via subosito/flutter-action
  with `flutter-version` pinned". Research confirmed `flutter-version-file`
  requires an EXACT `environment.flutter` value in pubspec.yaml — ours
  declares only an SDK range (`sdk: ^3.11.4`), so the exact-pin form is the
  reproducible one. Channel `stable` + exact version = deterministic.
- **Go pinned to 1.26.5 (installed), not `go-version-file: go.mod`:**
  research (actions/setup-go@v7 README): `go-version-file` reads the `go`
  directive (or the `toolchain` directive if present — go.mod has none) and
  resolves it against go.dev downloads; a version that is not a released
  tag fails setup. go.mod's `go 1.26.2` is a **minimum-version directive**;
  the installed toolchain is **1.26.5** (verified `go version`). Per the
  mission ("pin the INSTALLED go version… and document the mismatch") the
  pin is `'1.26.5'`; building go.mod-declared `go 1.26.2` code with a newer
  toolchain is valid Go semantics. When go.mod's directive catches up, the
  pin can switch to `go-version-file` (documented in README + log).
- **`dart analyze` run directly, no third-party action:** the pinned SDK
  ships the analyzer; this is the standard pattern and matches the local
  `make flutter-analyze`/`make check` gate exactly (local parity = CI).
- **`flutter test test/` only in `analyze`:** the mission scopes the job to
  the unit suite; `integration_test/` flows are hermetic but run under
  `flutter test` and the mission defers them to M-21/build (documented in
  README — linux runner would need xvfb/`-d linux` for some flows).
- **`backend-static` = make test-backend-static + opt-008 + check_ports +
  secrets-check:** the Makefile's `test-backend-static` target covers
  opt-005+opt-007 only (MKE-06); opt-008 (make-contract/migrate probes) is a
  fourth static gate that the mission lists explicitly, so it is invoked
  directly (`bash test/opt-008-makefile-static.sh`) — same hermetic shape.
  opt-007's `docker compose config --quiet` parse sections run on
  ubuntu-latest (docker preinstalled; `compose config` is daemon-less) and
  skip-with-note where docker is absent — the gate is green either way.
- **`tools/check_ports.sh --strict` needs no docker — VERIFIED by
  inspection:** the script is pure bash/awk/grep/find over repo files
  (agrep of the 432-line script: zero `docker`, `curl`, `nc` invocations —
  only file parsers + `sort`/`find`/`awk`). No guard needed; documented.
- **`make secrets-check` works in CI:** `tools/check_secrets.sh` uses
  `git grep` over TRACKED files — `actions/checkout` provides a git repo;
  untracked `.env` files don't exist on a fresh checkout, and the tracked
  `supabase/.env.local` dev sources are allowlisted by design (M-13).
- **Zero secrets in ci.yml:** the PR gates need no credentials (no
  dart-defines required — test targets run define-free by design, M-11; the
  app's `String.fromEnvironment` defaults are empty). The secrets surface is
  M-21 (build dart-defines via CI secrets) and M-22 (release §6 names).
- **Artifacts upload `if: always()`:** a red suite must still produce its
  report for inspection; `--machine`/`-json` outputs are the standard
  machine-readable formats for later dashboards.
