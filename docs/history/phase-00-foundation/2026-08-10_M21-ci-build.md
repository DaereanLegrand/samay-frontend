## Decisions made and why

- **`supabase/.env` is gitignored — the mission's "committed .env" premise
  does not hold.** Verified: `git check-ignore supabase/.env` → IGNORED (the
  file holds local dev values; `.gitignore` `.env` matches any level).
  Committed dev values exist in `supabase/.env.local` (tracked:
  `SUPABASE_URL` + `SUPABASE_ANON_KEY`) and in the opt-suite defaults. So the
  workflow materializes the stack env at runtime from TRACKED sources:
  compose precedence is shell env > `.env` file, so exporting via
  `$GITHUB_ENV` is equivalent to having a `.env` — no file written, no
  secrets, no literals.
- **Kong keys are `sed`-extracted from `test/opt-001-rls-security.sh`, not
  duplicated.** The live opt-tests send `ANON_KEY`/`SERVICE_KEY` defaulted to
  the dev values on lines 24–25; the stack must accept exactly those keys
  (M-03 alignment, pinned by opt-007 §8.4). Extraction keeps the single
  source of truth and keeps `.github/` literal-free (secrets-check P1/P3
  allowlists do NOT cover `.github/` — a hardcoded key there would fail
  `make secrets-check` once tracked). First awk attempt grabbed the whole
  `${ANON_KEY:-…}` shell-default — fixed with the `sed` form
  `s/^ANON_KEY="${ANON_KEY:-\([^"}]*\)}"$/\1/p` (verified locally:
  extraction returns exactly the two documented dev keys).
- **Migration flow — the mission asked to READ it; here is the verdict:**
  SELFHOSTING §5: "`docker compose up -d --wait` alone does not apply
  migrations (the `volumes/db/init` dir is currently empty — no auto-init
  SQL)". Verified: `supabase/volumes/db/init/` is empty in BOTH stacks, and
  `make supabase-docker-reset` (down + rm volumes + up) does NOT migrate
  either (only the interactive `reset.sh` does, and CI cannot type
  "reset"). Therefore the CI sequence is `make supabase-docker-start` →
  **`bash supabase/migrate.sh`** (idempotent migrations + seed; the
  SELFHOSTING §4 runbook step 4) → `make supabase-db-test` →
  `make supabase-backend-tests`. `supabase-docker-reset` is deliberately
  skipped: every run is a fresh runner with fresh bind dirs (docker creates
  missing bind sources) — nothing to reset. The full sequence
  grep-compares 1:1 to the §4 runbook.
- **pgTAP via the Supabase CLI in CI (not psql):** the M-12-researched
  canonical invocation `supabase db test --db-url …54382…` needs only the
  CLI binary + docker; `supabase/setup-cli@v3` pins `version: 2.113.0` (npm
  mirror of the CLI tags — README verified via webfetch). pg_prove runs on
  the host network → reaches `127.0.0.1:54382`; docker on ubuntu-latest
  supports host networking. First run pulls `supabase/pg_prove:3.36`.
- **`flutter test integration_test/` needs no xvfb/device — verified by
  mechanism:** `flutter test` compiles the flow for and runs it on the
  bundled headless `flutter_tester` device (no display server, no desktop
  shell). This is the exact mechanism ci.yml's `analyze` job already uses for
  `flutter test test/` (1624/0, M-20). The hermetic flows (in-memory Supabase
  harness, `integration_test/support/fake_supabase.dart`) need no stack, so
  the step runs after the backend suite per the mission's order.
  `make test-integration` (runner.sh) is NOT invoked: its retry/skip logic
  exists for the macOS-desktop "Failed to foreground app" flake, which cannot
  occur on the linux flutter_tester.
- **Ports as explicit job env:** compose `${VAR:-default}` already defaults to
  the approved map; declaring `POSTGRES_PORT`…`ANALYTICS_PORT` + `COMPOSE_FILE`
  in the job env makes the contract visible and guards against default drift.
  Nothing on ubuntu-latest binds 54382/54386/54381/54384/54388/54443 (runner
  services use ephemeral/standard ports; docker runs in its own namespace) —
  no collision with the runner or with Juega's ports (never used).
- **JDK 17 (temurin) verified from the repo:** `gradle-wrapper.properties` →
  `gradle-9.4.1-bin.zip` (Gradle 9 requires JVM 17+), `settings.gradle.kts` →
  AGP 8.11.1 (requires 17+), `build.gradle.kts` → `sourceCompatibility =
  JavaVersion.VERSION_17`. Mission's "temurin 17 — verify" → verified.
- **Debug APK only:** release builds need the signing config (currently the
  debug keystore per `build.gradle.kts:37`; the real keystore contract is
  M-27 wiring + M-18 placeholders + §6 R22–R24 secrets). No dart-defines on
  purpose: `flutter build apk` compiles define-free fine (I-34:
  `String.fromEnvironment` defaults empty, the app fails fast at RUNTIME —
  the build itself is a compile smoke + artifact), and the §3.2
  defines-via-CI-secrets story belongs to M-22's release job. **No IPA:** a
  macOS runner is required — M-22's release.yml.
- **Zero secrets in build.yml:** no `${{ secrets.* }}` references (none
  needed), no key literals (runtime derivation), no `your_supabase`, no
  `APPLE_PASSWORD`-shaped lines. Post-commit `make secrets-check` stays green
  (verified by grepping the new file against P1–P6 patterns).

## MISTAKE / gotcha

- **MISTAKE (hit + fixed during verification):** my first key-extraction draft
  used `awk -F'"'` and returned the WHOLE `${ANON_KEY:-sb_publishable…}`
  shell-default instead of the key — the value sits inside the `${VAR:-…}`
  expansion, between the quotes, so it is the expansion that is field 2, not
  the key. Switched to the `sed` capture form
  `s/^ANON_KEY="${ANON_KEY:-\([^"}]*\)}"$/\1/p` — verified locally to return
  exactly the documented dev keys. (Caught by a local dry-run of the
  extraction before the workflow was written.)
- **Gotcha (checked, not hit):** GitHub steps do not share shell exports —
  each `run:` is a fresh process. The stack env therefore goes through
  `$GITHUB_ENV`, which persists across steps (compose reads it as process
  env; precedence shell > `.env` file).
- **Gotcha (checked, not hit):** `migrate.sh` does `source .env 2>/dev/null
  || true` — on a fresh checkout `supabase/.env` is absent and the guard
  continues; DB_URL defaults to 54382 (M-10 pinned).
- **Gotcha (research):** `supabase/setup-cli` is at **v3** (npm-based,
  `version` input = npm-published CLI version; requires Node 20+ — present on
  ubuntu-latest), not v1/v2; M-12's CLI verification (2.113.0) maps to
  `version: 2.113.0`.
- **Gotcha (checked, not hit):** `volumes/db/init` is mounted at
  `/docker-entrypoint-initdb.d` but EMPTY — on a fresh bind dir (CI) the
  postgres image's entrypoint finds nothing to run; migrations come from
  migrate.sh. This is the current repo state, not a CI bug.
- **Pre-existing (reported, NOT fixed — out of scope):** the android gradle
  wrapper is INCOMPLETE — `android/gradle/wrapper/` tracks only
  `gradle-wrapper.properties`; `gradlew`, `gradlew.bat` and
  `gradle-wrapper.jar` are absent from the tree. `flutter build apk` on a
  fresh checkout may fail to bootstrap gradle unless flutter_tools
  regenerates the wrapper (recent Flutter does auto-generate missing
  wrappers, but this is unverified for 3.44.1 + gradle 9.4.1). This is
  M-27's file (FILE-OWNERSHIP: `android/**` gradle) — handoff written in the
  log + README risk note.
